大概五六年前,接手过一个电商下单系统,那会儿它还是一个标准的大单体:订单、库存、支付、会员全都塞在一个 Spring Boot 工程里,一个 war 包打天下。业务起来之后,问题慢慢浮出来了——**改一行会员逻辑,得连订单、支付一起全量回归;发版要凑齐四个模块都 ready,谁也不敢先动**。更麻烦的是,一次大促前的压测,库存扣减的慢 SQL 直接把整个下单接口拖垮了,会员那边什么都没做,也跟着一起超时。

那次之后,团队决定开始拆。这篇文章,就把从单体到微服务这一路的经验、踩过的坑、还有那些绕不开的新问题,一次讲透。

## 一、单体架构,到底卡在哪

单体不是原罪,它在业务早期几乎是唯一正确选择:部署简单、事务好管、调用链短。真正出问题,是业务复杂度越过某个临界点之后:

- **代码耦合**:改一处牵动全身,回归成本线性增长
- **部署耦合**:一个模块发版,整个系统跟着重启,发版窗口互相等
- **技术栈锁死**:想做局部技术演进(比如换存储、上新技术)困难重重
- **扩展粒度粗**:只能整机扩容,CPU 密集的模块和 IO 密集的模块捆在一起,资源浪费

一句话:**单体的问题,本质是"耦合"和"扩展粒度"的问题,而不是"单体"这个名词的问题**。

## 二、怎么拆:边界比技术更重要

拆微服务的难点从来不在技术,而在**边界怎么划**。见过不少团队一上来就按"技术分层"拆(拆成 controller 服务、service 服务),结果服务之间调用深度翻倍,延迟翻倍,还不如不拆。

一个基本原则:**按业务能力(business capability)拆,而不是按技术职责拆**。回到下单系统,自然的分界是这样的:

| 服务 | 职责边界 | 核心数据 |
|------|---------|---------|
| 订单服务 | 订单生命周期、状态流转 | 订单表 |
| 库存服务 | 库存扣减、锁定、回补 | 库存表 |
| 支付服务 | 支付单、退款、对账 | 支付流水 |
| 会员服务 | 用户资料、等级、权益 | 会员表 |

判断边界是否合理,有个很实用的信号:**如果两个"服务"之间总是需要一起改、一起发布、一起回滚,那它们大概率不该拆开**——高频联动的模块,强行拆开只会得到"分布式单体"(distributed monolith),拆了等于白拆,还多了一堆网络调用的开销。

> 拆分的黄金法则:**高内聚、低耦合**。内部逻辑聚在一起,对外只暴露稳定的接口契约。

## 三、拆分落地,先从数据开始

确定了边界,落地的第一步往往不是写新服务,而是**把数据库拆开**。共享同一个库,是所有服务互相牵制的根源。

常见做法分三步走,逐步、可控地演进,而不是一夜之间推倒重来:

1. **先拆读**:新服务先通过只读副本访问数据,把查询逻辑迁过去
2. **再拆写**:用双写 + 数据校验的方式过渡,新服务接管自己的写入
3. **最后断链接**:稳定后,老服务彻底不再直接碰这张表

这个过程中,一个关键约束是**数据库不能是共享的**:每个服务只允许访问自己的库,跨服务的数据一律通过接口,而不是直接 join 别人的表。见过因为图省事跨库 join,最后线上查不出数据归属、越改越乱的反面案例。

## 四、注册发现:服务之间怎么互相找到

拆成十几个服务后,第一个要解决的就是**服务之间怎么互相找到彼此**。写死 IP 的玩法在微服务里活不过一版,一个服务的扩容缩容、故障迁移都会让写死的地址立刻失效。

核心就是**注册中心**。以 Spring Cloud 的 Eureka 为例,基本用法:

```yaml
# 服务端(Eureka Server)
server:
  port: 8761
eureka:
  client:
    register-with-eureka: false   # 自己是注册中心,不注册自己
    fetch-registry: false
```

```yaml
# 客户端(业务服务)
spring:
  application:
    name: order-service           # 服务名就是唯一标识
eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka
```

服务启动时把 `服务名 + 地址` 注册上去,调用方通过服务名拿地址:

```java
@FeignClient(name = "inventory-service")   // 通过名字调用,IP 由注册中心解析
public interface InventoryClient {
    @PostMapping("/stock/deduct")
    Result deduct(@RequestBody DeductRequest request);
}
```

再叠加客户端负载均衡(Ribbon/LoadBalancer),**扩容缩容、故障下线都能被自动感知**,调用方无感知。这是微服务最基础的"呼吸系统"。

## 五、限流熔断:别让一个服务拖垮整个链路

拆开之后,一个更现实的风险出现了:**一个服务慢,会像多米诺骨牌一样拖垮整条调用链**。这就是"雪崩"。

两种武器缺一不可:

- **限流**:控制单位时间内的请求量,超出就直接拒绝,保护自己不被压垮
- **熔断**:当某个下游错误率/延迟超过阈值,主动"切断"对它的调用,快速失败,给它喘息恢复的时间

用 Sentinel 给下单接口加限流,配置很直观:

```java
// 下单接口,单机 QPS 上限 200,超出直接拒绝
initFlowRule("place-order", 200);
```

熔断(以 Resilience4j 为例):

```java
CircuitBreaker cb = CircuitBreaker.ofDefaults("inventory");
// 错误率超过 50% 时熔断,快速失败 10 秒后再尝试
```

```yaml
resilience4j:
  circuitbreaker:
    instances:
      inventory:
        failure-rate-threshold: 50
        wait-duration-in-open-state: 10s
```

一个基本原则:**限流保护的是自己,熔断保护的是下游和整个系统**。线上最怕的不是某个接口慢,而是慢接口把线程池占满,连带健康接口一起超时——所以凡是调用外部服务的,都要有熔断兜底。

## 六、分布式带来的新问题:旧的假设全被打破

拆完不是终点,反而是**真正麻烦的开始**。单体里那些"想当然"的保证,在分布式下全失效了:

| 单体里的假设 | 分布式下的现实 |
|-------------|--------------|
| 一个事务搞定所有一致性 | 跨服务没有共享事务,要上分布式事务/最终一致 |
| 一次调用就一次调用 | 一个请求横跨十几个服务,延迟、失败面都放大了 |
| 日志查一下就知道哪错了 | 链路分散,定位问题要靠全链路追踪 |
| 本地时钟就是准的 | 各机器时钟漂移,依赖本地时间会出诡异 bug |

其中**分布式事务**是最难啃的骨头。经验是:**能避免就避免,优先设计成最终一致**。下单扣库存这个经典场景,踩过的坑总结成一条原则——下单成功、扣库存失败时,不要指望一个分布式锁/事务一把梭,而是用**消息 + 补偿**:

```java
// 下单服务:本地事务落单 + 发消息
@Transactional
public void placeOrder(Order order) {
    orderMapper.insert(order);
    mq.send("order-created", order.getId());   // 本地事务内发消息
}

// 库存服务:消费消息扣库存,失败则重试或人工补偿
@RabbitListener(queues = "order-created")
public void deductStock(Long orderId) {
    if (!stockService.deduct(orderId)) {
        retryOrCompensate(orderId);            // 扣不动就走补偿
    }
}
```

核心思想:**用"最终一致 + 可重试 + 可补偿"替代"强一致 + 大事务"**。分布式一致性没有免费的午餐,选强一致就要付性能代价,选最终一致就要接受短时间的数据不一致,得想清楚业务能不能容忍。

## 七、什么时候该上,什么时候别上

说了这么多,回到最该先回答的问题:**到底什么时候才该拆微服务**。判断标准很朴素,满足越多越该上:

- 团队规模是否大到单体已经互相阻塞、合并冲突天天有
- 业务是否有**清晰的边界**可以拆(拆不动的边界说明还不成熟)
- 是否备好了**基础设施**:容器、CI/CD、监控告警、链路追踪
- 是否扛得住分布式带来的复杂度(事务、一致性、运维)

如果上面大多不满足,**"模块化的单体"往往才是更优解**——先在单体内部用清晰的包边界、模块依赖约束把代码理顺,等真正的痛感出现再拆。

## 写在最后

回头看这五六年的演进,最深的体会是一句话:**微服务不是银弹,它不解决架构问题,它只是把"代码里的耦合"换成"网络里的调用"**。拆之前先想清楚边界和代价,拆之后把注册发现、限流熔断、可观测性这些"配套工程"补齐——架构没有最好,只有最合适。先立规矩,再动手拆。
