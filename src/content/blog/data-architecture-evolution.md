> 数据架构不是一次设计到位的——是随着数据量增长逐步演进的。10GB 用单库，100GB 用读写分离，1TB 用分库分表，10TB 用数据仓库，10PB 用数据湖。每个阶段的瓶颈不同、解法不同、迁移成本不同。这篇文章梳理从单库到数据湖的完整演进路线，以及在每个阶段该做什么、不该做什么。

## 一、数据架构的五阶段演进

```mermaid
flowchart LR
    S1["阶段一<br/>单库<br/>< 100GB"] --> S2["阶段二<br/>读写分离<br/>< 500GB"]
    S2 --> S3["阶段三<br/>分库分表<br/>< 10TB"]
    S3 --> S4["阶段四<br/>数据仓库<br/>< 1PB"]
    S4 --> S5["阶段五<br/>数据湖<br/>无上限"]
```

## 二、阶段一：单库（< 100GB）

### 2.1 架构

```
应用 → MySQL 单实例（主库）
  - 读写都在主库
  - 简单、运维成本低
  - 瓶颈：单点写入、读扩展受限
```

### 2.2 优化手段（拆库之前先做这些）

| 优化 | 效果 | 成本 |
|------|------|------|
| 合理建索引 | 10-100x 查询提升 | 低 |
| 慢查询优化 | 消除瓶颈 SQL | 低 |
| 引入 Redis 缓存 | 读 QPS 提升 10x | 中 |
| 垂直拆分（拆表） | 热点表独立 | 中 |

**原则**：不要过早分库分表。80% 的系统在单库 + 缓存 + 索引优化后就够用了。

## 三、阶段二：读写分离（< 500GB）

### 3.1 架构

```
应用 → 读写分离中间件（ShardingSphere / MyCat / ProxySQL）
  → 写 → 主库
  → 读 → 从库 1, 从库 2, 从库 3（负载均衡）

主从同步：binlog → 异步复制（延迟毫秒~秒级）
```

### 3.2 核心问题：主从延迟

```
问题：写完主库 → 马上读从库 → 从库还没同步 → 读到旧数据

解法：
  1. 强制路由：写后 N 秒内的读请求走主库
  2. 半同步复制：主库写成功后至少等一个从库确认
     → RPO = 0，但写延迟增加
  3. 接受最终一致：业务层容忍秒级延迟
```

## 四、阶段三：分库分表（< 10TB）

### 4.1 何时该分

| 指标 | 分库阈值 | 分表阈值 |
|------|---------|---------|
| 单库数据量 | > 500GB | — |
| 单表行数 | — | > 2000 万 |
| 单表大小 | — | > 2GB |
| 写入 QPS | > 5000 | — |
| 慢查询比例 | > 5%（优化后） | > 5%（优化后） |

### 4.2 分片键选择

```
分片键 = 路由字段（决定数据去哪个库/表）

好的分片键：
  - 查询最常用的字段（避免跨分片查询）
  - 数据分布均匀（避免热点分片）
  - 不常变化（变化会导致数据迁移）

常见分片键：
  用户维度 → user_id（同一用户的数据在一个分片）
  订单维度 → order_id（哈希分片，均匀分布）
  时间维度 → created_at（按时间范围分片，适合归档）

复合分片键：
  user_id % 16 → 库
  order_id % 64 → 表
  → 同一用户的订单在同一库（本地 JOIN），分散在不同表
```

### 4.3 分库分表的代价

| 问题 | 解法 |
|------|------|
| 跨库 JOIN | 应用层组装 / 宽表 / ES |
| 分布式事务 | Seata / 消息队列最终一致 |
| 全局唯一 ID | 雪花算法 / 号段模式 |
| 扩容迁移 | 双写 + 数据校验 + 切流 |
| 分页查询 | 禁止深度分页 / ES 替代 |

## 五、CDC：数据同步的核心技术

### 5.1 CDC 是什么

```
CDC（Change Data Capture）：捕获数据库的变更事件（INSERT/UPDATE/DELETE），
实时同步到其他系统（缓存、ES、数仓、另一个库）。

流程：
  MySQL binlog → Canal/Debezium → Kafka → 消费者（ES/Flink/另一个库）
```

### 5.2 工具对比

| 工具 | 原理 | 延迟 | 适用 |
|------|------|------|------|
| **Canal** | 伪装 MySQL Slave，解析 binlog | 秒级 | MySQL → 其他系统 |
| **Debezium** | 基于 Kafka Connect，支持多数据库 | 秒级 | 多数据源统一 CDC |
| **Flink CDC** | Flink 直接读 binlog，支持全量+增量 | 毫秒~秒级 | CDC + 实时计算一体 |

### 5.3 双写迁移方案

```
分库分表迁移的标准流程（不停机）：

Phase 1: 双写
  应用同时写旧库和新库（新库为备）
  旧库为主，新库异步追平数据（CDC）

Phase 2: 数据校验
  对比旧库和新库的数据一致性
  不一致 → 修复 → 重新校验

Phase 3: 读切流
  读流量从旧库切到新库（灰度 10% → 50% → 100%）
  回滚方案：随时切回旧库

Phase 4: 写切流
  写流量从旧库切到新库
  旧库保留一段时间（回滚兜底）

Phase 5: 下线旧库
  确认新库稳定运行 1-2 周后，下线旧库
```

## 六、阶段四：数据仓库（< 1PB）

### 6.1 数仓分层

```
ODS（操作数据层）：
  → 原始数据，和源系统结构一致
  → 来源：CDC 同步的 MySQL 数据

DWD（明细数据层）：
  → 清洗后的明细数据
  → 维度建模（事实表 + 维度表）
  → 去重、标准化、维度关联

DWS（汇总数据层）：
  → 按主题汇总（日/周/月粒度）
  → 宽表（把多个事实表的指标合并）

ADS（应用数据层）：
  → 面向具体报表/应用
  → 高度聚合，直接给 BI 工具用
```

### 6.2 离线 vs 实时

| 维度 | 离线（Hive/Spark） | 实时（Flink） |
|------|-------------------|--------------|
| 延迟 | 小时~天级 | 秒~分钟级 |
| 成本 | 低（批处理） | 高（持续计算） |
| 准确性 | 高（全量计算） | 中（近似计算） |
| 适用 | T+1 报表、历史分析 | 实时大屏、实时风控 |

## 七、阶段五：数据湖（无上限）

### 7.1 数据仓库 vs 数据湖

| 维度 | 数据仓库 | 数据湖 |
|------|---------|--------|
| 数据格式 | 结构化（表） | 任意格式（结构化+半结构化+非结构化） |
| Schema | Schema-on-Write（写入时定义） | Schema-on-Read（读取时定义） |
| 存储成本 | 高（列存 + 索引） | 低（对象存储，S3/HDFS） |
| 查询性能 | 高（预优化） | 中（按需优化） |
| 适用 | 结构化数据分析 | 原始数据存档 + 探索性分析 |

### 7.2 湖仓一体

```
数据湖仓（Lakehouse）= 数据湖的存储成本 + 数据仓库的查询性能

代表：
  Apache Iceberg：开放表格式，支持 ACID 事务 + 时间旅行
  Apache Hudi：增量数据处理，支持 upsert
  Delta Lake（Databricks）：ACID + 统一批流处理

架构：
  原始数据 → 数据湖（S3/HDFS，Parquet/ORC 格式）
  → Iceberg/Hudi 表格式（ACID + 索引）
  → Spark/Flink/Trino 查询（和查数仓一样）
```

## 八、技术选型决策树

```
数据量 < 500GB，读写比 > 10:1？
  → 读写分离 + Redis 缓存

数据量 > 500GB 或写 QPS > 5000？
  → 分库分表（ShardingSphere）

需要跨库查询 / 复杂分析？
  → CDC 同步到 ES（搜索）或 Doris（分析）

需要 T+1 报表？
  → CDC → Kafka → Flink/Spark → 数仓（Hive/Doris）

需要实时大屏 / 实时风控？
  → Flink CDC → Flink 实时计算 → Doris/ES

数据量 > 1PB？
  → 数据湖（S3 + Iceberg）+ Trino 查询
```

## 结语

数据架构演进不是一次性设计——是跟随业务增长逐步升级。

> 单库解决起步问题，读写分离解决读扩展，分库分表解决写瓶颈，数仓解决分析问题，数据湖解决存储成本。每一步都有迁移成本——不要过早做下一步，也不要太晚做下一步。

架构师的判断力在于：知道当前阶段该做什么，也知道什么时候该准备下一步。
