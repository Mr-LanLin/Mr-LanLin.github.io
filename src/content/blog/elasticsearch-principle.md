> ES 被当成「什么都能查」的数据库用——这是最大的误用。ES 的强项是全文检索和聚合分析，不是事务、不是强一致、不是精确的 CRUD。把它当数据库用，迟早会在深度分页、数据一致性、写入性能上栽跟头。

## 一、倒排索引：ES 快的核心原因

### 1.1 正排 vs 倒排

```
正排索引（MySQL）：
  文档 1: "今天天气很好"
  文档 2: "明天天气不错"
  查"天气" → 全表扫描所有文档 → O(N)

倒排索引（ES）：
  "今天" → [文档1]
  "天气" → [文档1, 文档2]
  "很好" → [文档1]
  "明天" → [文档2]
  "不错" → [文档2]
  查"天气" → 直接定位到 [文档1, 文档2] → O(1)
```

**代价**：写入时要更新倒排表（分词 → 建索引），所以 ES 的写入比读取慢。读多写少的场景最适合 ES。

### 1.2 段（Segment）与合并

```
新文档写入：
  → 写入内存 Buffer
  → Buffer 满（默认 1GB）→ flush 到磁盘，生成一个不可变的 Segment
  → 新 Segment 加入 Segment List
  → 旧 Segment 不会被修改（immutable）

后台合并：
  → 小 Segment 合并成大 Segment（减少文件数，提升查询效率）
  → 合并过程中删除的文档被物理清除
  → 合并是 IO 密集操作，会影响写入性能
```

**生产教训**：频繁小批量写入会生成大量小 Segment，合并压力大。批量写入（Bulk API，每次 5-15MB）比逐条写入效率高 10 倍以上。

## 二、分片机制：扩展性和一致性的权衡

### 2.1 主分片与副本

```
Index: orders
  Primary Shard 0 → Node A
    Replica Shard 0 → Node B  (副本)
  Primary Shard 1 → Node B
    Replica Shard 1 → Node C  (副本)
  Primary Shard 2 → Node C
    Replica Shard 2 → Node A  (副本)

查询时：可以读主分片或副本（轮询）→ 读吞吐 = 节点数 × 副本数
写入时：必须写主分片 → 同步到副本 → 写吞吐 = 主分片数
```

**关键约束**：主分片数创建后不能改（除非 reindex）。副本数可以动态调整。

### 2.2 分片数怎么设

| 分片数 | 优点 | 缺点 |
|--------|------|------|
| 太少（1-2） | 合并效率高、跨分片查询少 | 写入吞吐低、无法充分利用多节点 |
| 适中（3-10） | 写入吞吐和查询效率平衡 | 需要评估数据增长 |
| 太多（>100） | 写入吞吐高 | 合并开销大、集群状态慢、查询协调成本高 |

**经验值**：每个分片 20-50GB。一个 500GB 的索引设 10-25 个主分片。每个节点的分片数不超过 20-25 个（太多会影响集群稳定性）。

## 三、写入性能优化

### 3.1 写入链路

```
Client → Coordinating Node → Primary Shard → (replicate) → Replica Shard
                              ↓
                        写入 Translog（预写日志，防丢失）
                              ↓
                        写入 In-Memory Buffer
                              ↓
                        refresh（默认 1s）→ Buffer → Segment → 可搜索
                              ↓
                        flush（默认 30min 或 Translog 满）→ Segment → 磁盘
```

### 3.2 优化手段

| 参数 | 默认值 | 优化值 | 效果 |
|------|--------|--------|------|
| `refresh_interval` | 1s | 30s（批量导入时） | 减少 Segment 生成，提升写入 5-10x |
| `number_of_replicas` | 1 | 0（导入时）→ 1（导入后） | 导入时不写副本，速度翻倍 |
| `translog.durability` | request | async | 异步刷 Translog，丢少量数据换性能 |
| Bulk size | — | 5-15MB / 1000-5000 条 | 减少网络开销 |

**批量导入的标准流程**：
1. 建索引时 `replicas=0`、`refresh_interval=-1`（不自动刷新）
2. Bulk 写入
3. 写入完成后 `replicas=1`、`refresh_interval=1s`
4. 手动 `POST /index/_refresh`

## 四、深度分页：ES 最大的坑

### 4.1 from + size 的代价

```sql
-- 查第 1000 页，每页 10 条
GET /orders/_search
{ "from": 10000, "size": 10 }
```

ES 的处理方式：**每个分片都要取出前 10010 条，排序后返回给协调节点，协调节点再全局排序取第 10001-10010 条**。

```
5 个分片 × 10010 条 = 50050 条在网络上传输
协调节点排序 50050 条 → 取 10 条
内存占用 = O(from + size) × 分片数
```

from=100000 时：5 个分片 × 100010 条 = 50 万条 → OOM。

**ES 默认限制 `max_result_window=10000`**——不是 bug，是保护。

### 4.2 三种替代方案

| 方案 | 原理 | 适用场景 | 限制 |
|------|------|---------|------|
| **Scroll** | 快照 + 游标，每次取一批 | 全量导出、数据迁移 | 不是实时数据，有快照成本 |
| **Search After** | 基于上一页最后一条的排序值 | 实时深度分页 | 必须有序字段，不能跳页 |
| **Scroll + 写临时表** | 导出到 MySQL 再分页 | 需要随机跳页的导出 | 架构复杂 |

**架构师的判断**：如果需要随机跳页（如「跳到第 500 页」），ES 做不了——在 ES 里做完聚合/过滤后，把结果导出到 MySQL/Redis，由关系型数据库处理分页。

## 五、集群脑裂

### 5.1 什么是脑裂

```
3 节点集群：Node A (Master), Node B, Node C

网络分区：
  Group 1: Node A  (认为自己是 Master)
  Group 2: Node B, Node C (选举 Node B 为 Master)

两个 Master 同时接受写入 → 数据分叉 → 网络恢复后数据冲突
```

### 5.2 解法：法定人数

```yaml
# ES 7.x+ 自动处理（3 节点集群的法定人数 = 2）
# 但理解原理很重要：
#
# 法定人数 = (master_eligible_nodes / 2) + 1
# 3 节点 → 法定人数 = 2（需要 2 票才能选 Master）
# 5 节点 → 法定人数 = 3
# 脑裂时，只有一方能凑够法定人数
```

**生产教训**：Master 节点和数据节点分离。3 个专用 Master 节点（不存数据）+ N 个数据节点。Master 节点不参与数据读写，避免因数据负载导致 Master 心跳超时。

## 六、ES 不是万能的

| 能力 | ES | 更适合的方案 |
|------|-----|------------|
| 全文搜索 | ✅ 强项 | — |
| 聚合分析 | ✅ 强项 | — |
| 日志检索 | ✅ 强项 | — |
| 精确 CRUD | ⚠️ 可以但不擅长 | MySQL/PostgreSQL |
| 事务 | ❌ 不支持 | MySQL/PostgreSQL |
| 深度分页 | ❌ 不支持 | MySQL |
| 强一致 |  最终一致 | MySQL（主从） |
| 关联查询 | ❌ 不支持 JOIN | MySQL / 应用层组装 |

**选型决策**：
- 搜索 + 分析 → ES
- 搜索 + 事务 → MySQL（全文索引）+ ES（搜索），双写
- 搜索 + 关联查询 → 数据同步到 ES，查询走 ES，关联查 MySQL

## 结语

ES 是一个优秀的搜索引擎，不是一个万能的数据库。

> 倒排索引给了 ES 全文搜索的能力，分片机制给了它水平扩展的能力，但同时也带来了深度分页的困境、写入性能的瓶颈、脑裂的风险。知道 ES 擅长什么，更要知道它不擅长什么——这才是架构师选型的底线。
