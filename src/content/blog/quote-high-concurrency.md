> 从「扣减一次报价机会」说起，看稀缺额度、乐观锁、排名博弈如何被同一个字段串起来

## 引子

报价是招采里最像「战场」的一个动作。它有三个让工程师头疼的特质叠加在一起：

- **报价次数是稀缺资源**。每个承运商每轮只有有限的修改报价机会，每次改价都要扣一次，扣完就不能再动，而且扣减必须原子——不能多扣、不能漏扣、不能并发扣穿。
- **排名既敏感又必须可见**。承运商要能看到自己在对手里的位置，但过早暴露会诱发「卡点跟价」，过晚又失去竞价的意义。
- **最后时刻有洪峰，也有狙击**。截止前几分钟，几百上千个承运商同时刷新排名、同时改价；还有人卡在最后几秒压价，想打一个对手来不及反应的时间差。

要扛住这三件事，常规思路是各配一套机制：一个计数器、一把锁、一个排序任务。但这样越堆越重。更优雅的解法，是让**一个字段同时扮演三个角色**——这正是本文要讲的核心。

---

## 一、一个字段，三重身份

先说结论。在竞价报价里，「剩余报价次数」这个字段，可以被设计成同时承担三种职责：

| 身份 | 职责 | 解决的问题 |
|------|------|-----------|
| 额度计数器 | 每次报价减一，减到零就拒绝 | 报价次数是稀缺资源 |
| 分布式锁的版本号 | 单调递增，作为锁的「指纹」参与比较 | 锁释放时防误删、防过期错杀 |
| 数据库乐观锁版本号 | 更新时带上旧值做 CAS 比较 | 并发改价不互相覆盖 |

这是全文最想讲透的一点：**稀缺额度与并发控制，本质上是可以合二为一的。** 一个「次数」字段，它既在回答业务问题（你还有几次机会），又在回答并发问题（这次更新以哪个版本为准）。业务域和并发域在这个字段上重叠了，所以它天生适合做乐观锁的载体。

很多系统把「剩余次数」和「版本号」分开建两个字段，其实是把同一个事实重复表达了两遍。次数本身就是一种版本——它每次变化都是单调递减的，天然具备「旧值可比较」的特性。

---

## 二、身份之一：额度计数器，用 Redis 原子扣减

报价次数的扣减，最朴素的做法是「读出来、减一、写回去」。但这三个动作不是原子的，并发下会扣穿——两个请求同时读到 2，各自减一写回 2，等于没扣。

正确姿势是让「扣减」本身成为一个原子动作。Redis 的 `DECR` 天然就是原子的，一条命令完成「读、减、写」：

```text
剩余 = DECR(报价次数Key, 1)
if 剩余 < 0:
    INCR(报价次数Key, 1)      # 不足则补偿回去
    throw 剩余报价次数不足
```

`DECR` 返回的是扣减后的值，`< 0` 就说明「这最后一次不该扣」，再用 `INCR` 补偿回去。扣减即校验，一步到位，不存在读到脏值的窗口。

如果业务上还需要「先查再判断」这类更复杂的逻辑，就把它收进一段 Lua 脚本，让整个「校验 + 扣减」在 Redis 里作为一个整体原子执行，避免多条命令之间的竞争。

到这里，次数的「计数」身份解决了。但它的价值远不止计数。

## 三、身份之二：分布式锁的版本号，防误删也防过期错杀

最后时刻的洪峰里，同一标的的排名计算、同一承运商的改价，都需要串行化。用分布式锁时有个经典坑：**谁加的锁，谁才能删锁**。如果锁超时被自动释放，而业务还在跑，另一个请求抢到锁，前一个请求跑完回来「顺手」把锁删了——删的是别人的锁，串行化就失效了。

破解的办法，是给每次加锁生成一个唯一的「版本指纹」，释放时先比较指纹，一致才删。而报价次数恰好是一个天然的、单调递增的版本来源：

```text
版本号 = INCR(锁版本Key)          # 单调递增，全局唯一
SET(锁Key, 版本号, NX, 超时时间)   # 用版本号作为锁的 value

# 释放时：
if GET(锁Key) == 版本号:
    DEL(锁Key)                    # 指纹一致才释放
```

这里的关键不在「用 Redis 的 value 存指纹」这个技巧本身，而在于思想：**让一个单调递增的序号同时充当「锁的版本」，锁的正确释放就变成了一个可比较的 CAS 操作。** 次数字段提供的这个递增能力，让「锁」和「额度」共享了同一个版本来源，不需要再单独维护一套 UUID。

更进一步，如果释放和比较也要严格原子（比如过期边界上刚好被释放又重加），就把「比较 + 删除」也收进 Lua 脚本，让释放操作本身原子化。

## 四、身份之三：数据库乐观锁版本号，用 CAS 更新防覆盖

即便有了 Redis 层面的原子扣减，最终报价明细还是要落库。并发改价时，两个请求都可能「读旧值、各自计算、写回」，后写覆盖先写，导致报价次数、价格对不上。

这里不引入悲观锁（锁行、锁表都会拖垮吞吐），而是让次数字段再做一次乐观锁的版本号。更新语句带上旧值做 CAS 比较：

```text
UPDATE 报价明细
   SET 剩余次数 = 剩余次数 - 1, 报价 = #{新报价}
 WHERE 主键 = #{id}
   AND 剩余次数 = #{旧次数}     # 乐观锁：旧值不一致，更新不生效
```

影响行数等于 0，就说明这一行在「读」和「写」之间被别的请求改过了，也就是发生了并发冲突。这时候要么重试，要么直接告诉用户「报价已更新，请刷新后重试」。用「旧值不匹配」来兜住并发，比无脑加锁的吞吐高得多。

值得强调的是：**这里的版本号不需要额外的一列 `version`，报价次数自己就是版本。** 它每扣一次就变一次，天然满足乐观锁「比较旧值」的要求。把额度字段复用为乐观锁版本，是省掉一个字段、还顺手获得并发保护的一举两得。

至此，「次数」字段的三重身份讲完了。它的生命力在于：**一个单调递减的数值，同时是额度、是锁版本、是乐观锁版本，把「业务额度」和「并发协调」两个本来要各自维护的东西，收敛成了同一个事实。**

## 五、排名：延迟掀牌与反狙击

次数的故事讲完了，回到排名的博弈。

排名不能无条件实时展示。太早暴露，领先者会被无限「压一毛钱」式跟价；太晚，又失去引导意义。可调的做法是**延迟掀牌**：报价进入最后一段窗口（延迟竞价期）后，排名暂时隐藏，让「看到名次 → 精准跟价」这条路走不通。

与此同时，针对「最后几秒压价狙击」，还有一道**反狙击的自动延长**机制：

```text
当满足以下全部条件时，本轮报价时间自动顺延 N 分钟：
  1. 排名策略开启了「延迟竞价」
  2. 此刻已进入截止前的最后 X 分钟
  3. 第一名刚刚发生了变化（被人反超）
  4. 本轮尚未延过（防止无限延长）
```

第一名在最后时刻被反超，说明有人在打时间差。系统不直接判输，而是给被反超者一个还手的机会——顺延一段时间，并把所有人的剩余报价次数重置回策略全值。这个「顺延 + 重置次数」的组合拳，既守住了公平，又和前面的次数生命周期闭环接上了：**次数不是只减不增，延迟延长就是它的「重置点」。**

排名的可见性同样受这套节奏约束：延迟竞价窗口内隐藏名次，窗口结束后才释放真实排名，让信息按「竞争节奏」而不是「实时全开」来释放。

---

## 六、最后时刻的削峰：排队合并 + 异步化

最后时刻的洪峰，读（刷新排名）和写（改价）一起压过来。真正伤筋动骨的不是单次请求，而是「同一标的的排名被并发重复计算」。几十个改价事件，如果都各自触发一次全量排名，数据库会被打穿，且可能算出互相矛盾的名次。

两个手段把洪峰削下来：

**其一，排队合并。** 同一标的的排名事件不是并发抢算，而是「同一时刻只算一个，其余排队」。已经排队的请求，等当前这一次算完，再做一次合并计算即可，不需要每个事件都算一遍。于是「几十个并发事件」被收敛成「最多两次实际计算」，名次最终一致，吞吐却不被拖垮。

**其二，异步化。** 排名是报价链路上最重的一环，本不该拖慢报价的同步响应。报价落库成功即返回，排名计算通过消息队列异步触发，把「最后时刻的尖峰」在时间维度上摊开、在空间维度上合并。

排队的「合并」和消息的「异步」，本质是同一件事：**让重的、可后置的计算，从同步关键路径上剥离，再对同源请求做去重。**

---

## 收尾：把热点收敛成本地事实

回顾整条链路，可以提炼出三条放之四海而皆准的原则：

1. **稀缺额度要做成事务/原子内的生命周期，而不是全局计数器。** 报价次数用 Redis 原子扣减、用 `<= 0` 兜底、用取消与延长做补偿和重置，形成一个自洽的闭环。

2. **并发协调尽量复用已有的业务字段。** 一个单调变化的「次数」，同时充当额度、锁版本、乐观锁版本，省掉了 `version` 列，也省掉了一套 UUID 机制。这是「少即是多」——让一个字段承载多重语义，前提是这些语义在本质上是同一个事实。

3. **重的计算后置、同源请求合并。** 排名不实时算，而是轮次结束批量算、异步触发、排队合并；排名的可见性用「延迟掀牌」按竞争节奏释放。

报价场景的难，从来不在单次报价多复杂，而在于把「稀缺额度、乐观锁、排名博弈」这三件彼此纠缠的事，用最少的机制、最优雅的方式串起来。一个字段的三重身份，一套延迟掀牌 + 反狙击的节奏，一层排队合并 + 异步的削峰——这就是竞价报价在高并发下站得住的底气。
