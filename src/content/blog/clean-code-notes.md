Robert C. Martin 的《代码整洁之道》出版十几年了,里面的原则一点不过时。真正让人记住这本书的,不是它讲了什么新东西,而是它把那些"写代码时隐隐觉得不对劲、又说不清为什么"的感觉,一条条讲明白了。

挑几条影响最深的记下来。

## 一、先从一个真实场景说起

接手过一个订单模块,核心逻辑只有三百行,却花了整整一下午才敢动。倒不是业务复杂,而是长这样:

```java
void handle(int type, String d, int s, boolean f) {
    if (type == 1) {
        int x = Integer.parseInt(d);
        if (s > 100) {
            // 处理大额订单
            // 一堆 if else...
        } else {
            // 处理小额订单
        }
    } else if (type == 2) {
        // 退款逻辑
        // 又一百行...
    }
}
```

`d` 是什么?`s` 是什么?`f` 到底控制啥?每个参数都得翻遍上下文才能猜个大概。更麻烦的是,改一行就担心牵一发动全身——因为根本看不出这段代码的边界在哪。

这就是"坏味道"最直接的体验:**读不懂,就不敢动;不敢动,就只能越堆越烂**。

## 二、命名是最重要的事

> 好的命名胜过注释。变量、函数、类,名字应该**自己解释自己**。

上面那段代码,`d` 其实是"天数",`s` 是"金额",`f` 是"是否加急"。把名字写清楚,一半的复杂度当场消失:

```java
// 差:含义模糊
int d; // elapsed time in days

// 好:一目了然
int elapsedTimeInDays;
```

命名要能**回答三个问题**:它为什么存在、做什么事、怎么用。反过来,一旦取不出一个好名字,往往说明这段代码的结构本身就有问题——要么职责太杂,要么概念没想清楚。

一个基本原则:**改代码之前,先把名字改对**。名字改对了,边界自然就浮出来了。

## 三、函数要短小,只做一件事

"函数应该只做一件事"听着像废话,做起来难。判断标准其实很具体:

- 函数长度尽量控制在 20 行以内
- 参数越少越好,超过 3 个就该考虑封装成一个对象
- 每个函数保持**单一抽象层级**,别一会儿是"下单"一会儿是"拼 SQL"

把第一节那个 `handle` 拆开,对比一下:

```java
// 差:一个函数干太多事
void processOrder(Order o) {
    validate(o);
    saveToDb(o);
    sendEmail(o);
    log(o);
    // ...
}
```

```java
// 好:拆成一个个只做一件事的小函数
void processOrder(Order order) {
    if (!isValid(order)) {
        return;
    }
    persist(order);
    notifyCustomer(order);
    recordAudit(order);
}
```

拆完之后,读代码的人得到的是**一列能读懂的动作清单**,而不是一个需要脑内展开的黑箱。

## 四、注释是失败的信号

能用代码表达清楚的,就别写注释。好的注释解释**"为什么"**,而不是复述**"做了什么"**:

```java
// 好:解释为什么
// 这里不能并发,否则会导致订单状态错乱
synchronized (lock) { updateStatus(); }

// 差:复述代码
// 把 status 更新为 paid
status = "paid";
```

见过最坑的注释是**过期的注释**:代码改了,注释没改,后来的人照着注释理解,越看越糊涂。所以更推荐的做法是——**优先用清晰的名字让代码自解释,注释只留给那些代码表达不了的"为什么"**。

## 五、常见坏味道清单

《代码整洁之道》里列了一堆坏味道,挑几个线上最常见、也最容易改的:

| 坏味道 | 表现 | 处理手法 |
|------|------|---------|
| 命名模糊 | `d`、`tmp`、`data`、`result` | 改成能回答问题三要素的名字 |
| 函数过长 | 超过 20 行还在往下滚 | 按职责拆分,提取小函数 |
| 重复代码 | 两段几乎一样的逻辑 | 提取公共方法,消灭重复 |
| 神秘数字 | `if (type == 1)` | 换成有名字的常量或枚举 |
| 过期注释 | 注释和代码对不上 | 删掉,或改成解释"为什么" |
| 过长参数列表 | 参数超过 3 个 | 封装成参数对象 |

这张表的价值不在"背下来",而在**当成一个 checklist,每次 review 别人的代码、或回头 review 自己的代码时,扫一遍**。

## 六、一个能直接抄的重构示范

假设要处理"给用户发通知"的逻辑,原来长这样,字段名和魔法值满天飞:

```java
// 重构前:命名模糊 + 神秘数字 + 单一职责被破坏
void notify(int u, int t) {
    String msg = "";
    if (t == 1) {
        msg = "您的订单已发货";
    } else if (t == 2) {
        msg = "您的订单已退款";
    }
    // 发短信
    smsClient.send("138xxxx", msg);
    // 发站内信
    inboxClient.push(u, msg);
    // 记录日志
    logger.info("notify user " + u + " type " + t);
}
```

重构后,把类型换成枚举、把魔法值变成有名字的东西、再拆出单一职责:

```java
// 重构后:名字自解释,每个函数只做一件事
enum NotifyType {
    SHIPPED("您的订单已发货"),
    REFUNDED("您的订单已退款");

    private final String message;

    NotifyType(String message) {
        this.message = message;
    }

    public String message() {
        return message;
    }
}

void notify(int userId, NotifyType type) {
    String message = type.message();
    sendSms(userId, message);
    pushInbox(userId, message);
    recordAudit(userId, type);
}
```

同样一份逻辑,读起来的成本天差地别。这就是"整洁"最直接的收益:**代码先给人读,顺便给机器执行**。

## 写在最后

整洁不是洁癖,是**对后来者(包括半年后的自己)的尊重**。命名、短函数、克制注释,这三条性价比最高,也最好上手。下次提交前不妨问一句:"半年后回头看,还能一眼读懂吗?"——答不上来,就先停下来重构几行。
