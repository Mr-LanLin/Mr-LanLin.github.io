有次对账系统半夜拉出这么一条异常:**订单表里钱扣了,账户表里余额却没变**,两边差了几十笔,合计几万块。追到最后发现,是"先扣款、后改余额"两步跨了两个服务,扣款服务成功返回了,改余额那一步却因为下游超时失败——而扣款服务压根没回滚。

单体时代一句 `@Transactional` 兜底的事,拆成微服务之后,变成了一道躲不开的坎:**分布式事务**。这篇文章把几种主流方案从头到尾捋一遍,顺便说说踩过的坑和最终的选型判断。

## 一、为什么本地事务那套不灵了

本地事务能保证 ACID,靠的是数据库用**同一个连接、同一份日志**把操作串成一个原子单元。一旦业务跨了服务、跨了库,问题立刻冒出来:

- **没有统一的提交点**:两个库各自 commit,谁也不知道对方成没成
- **网络不可靠**:调用方拿到超时,不代表下游没执行——可能是执行了但响应丢了
- **没有共享锁**:本地事务的锁管不住另一个进程的写

更本质的约束是 **CAP**:一致性(C)和可用性(A)在分区(P)发生时只能二选一。分布式事务的每一种方案,说到底都是在"到底要多强的一致性、愿意为此付出多大代价"之间做取舍。

## 二、2PC / XA:把提交拆成两次握手

最经典也最"教科书"的方案,思路是把一次提交拆成**准备 + 提交**两步,由协调者(Coordinator)统一指挥:

```
协调者                    参与者 A              参与者 B
   |                          |                     |
   |--- 1. prepare ---------->|                     |
   |--- 1. prepare -------------------------------->|
   |<-- 都返回 ready ----------+--------------------|
   |--- 2. commit ------------>|                     |
   |--- 2. commit --------------------------------->|
```

**prepare 阶段**各参与者把事务写到 undo/redo 日志、占住资源,但不真正提交;**commit 阶段**协调者收到全部 ready 后,再通知大家提交。任何一个参与者在 prepare 返回 no,就全体 rollback。

这套东西数据库原生支持,就是 XA 事务,Java 里对应 `javax.transaction.xa` 那套接口:

```java
XAResource xaRes = conn.getXAResource();
Xid xid = new MyXid(...);
xaRes.start(xid, XAResource.TMNOFLAGS);  // 开始
// ... 执行本地 SQL ...
xaRes.end(xid, XAResource.TMSUCCESS);
int ret = xaRes.prepare(xid);            // 一阶段:准备
if (ret == XAResource.XA_OK) {
    xaRes.commit(xid, false);            // 二阶段:提交
} else {
    xaRes.rollback(xid);                 // 二阶段:回滚
}
```

**但它有硬伤**:

- **同步阻塞**:prepare 之后、commit 之前,参与者一直锁着资源,并发越高越明显
- **单点**:协调者挂了,所有参与者卡在中间态,俗称"悬挂"
- **不一致窗口**:协调者刚发出 commit 就宕机,一部分参与者提交了、一部分没提交,得靠人工对账兜底

> 强一致是有代价的。XA 适合对一致性要求近乎苛刻、但并发不高、流程简单的场景(比如银行核心的账户划转),放到高并发的交易链路里,锁和阻塞很快会把它压垮。

## 三、TCC:把事务逻辑交给业务自己写

2PC 的问题在于它想"通用",于是只能靠阻塞锁。TCC 换个思路:**既然只有业务方知道怎么预留、怎么回滚,那就让业务方自己实现**。

TCC 是 Try-Confirm-Cancel 三个动作:

| 阶段 | 动作 | 语义 |
|------|------|------|
| Try | 预留资源 | 检查 + 冻结,不真正扣减 |
| Confirm | 确认 | 真正执行,幂等 |
| Cancel | 取消 | 释放预留,幂等 |

```java
public interface TccAction {
    boolean tryMethod();       // 冻结额度 / 预占库存
    boolean confirmMethod();   // 真正扣减
    boolean cancelMethod();    // 释放冻结
}
```

拿"下单扣库存"举例:`try` 把库存从"可售"冻结到"冻结",`confirm` 把冻结的库存真正扣掉,`cancel` 把冻结的库存还回去。三步都要求**幂等**,因为网络重试会让同一动作执行多次。

**优点**是性能好、锁粒度由业务自己控制;**代价**是侵入性强——每一个参与事务的服务都得手写这三段逻辑,还得处理**悬挂**(try 没到、cancel 先到)和**空回滚**这些边角。见过有团队为了一个下单流程,给三四个服务都写了一堆 try/confirm/cancel,代码量和 bug 数都涨了一截。

> 一个基本原则:**只有资金、库存这类"预留-确认"语义天然清晰的链路,才值得上 TCC**;普通 CRUD 硬套 TCC,只会换来一堆别扭的补偿逻辑。

## 四、Saga:每个步骤自带补偿

Saga 的思路更朴素:**把一个大事务拆成一串有序的本地事务,每个本地事务都配一个反向的补偿操作**。前面成功了、后面失败,就从失败那步往回逐个执行补偿,把已经做的"撤销"掉。

```
步骤1 创建订单  →  步骤2 扣库存  →  步骤3 扣款
     ↓补偿:取消订单     ↓补偿:补回库存   (失败,触发补偿链)
```

它不追求强一致,而是**最终一致 + 补偿**。好处是全程无锁、适合跨很多服务的长流程(出行订票、电商下单这种);坏处是补偿逻辑要写好,而且**中间态对外可见**——用户可能看到订单"已创建"又变回"已取消"。

实现上有两种编排方式:

- **编排式(Choreography)**:服务之间靠消息互相触发,没有中心协调者,流程散落在各服务里
- **协调式(Orchestration)**:有一个 Saga 管理器统一推进步骤、记录状态,流程集中可控

> 更推荐的做法是**协调式**:流程长的时候,把"现在走到哪一步了"显式存下来,排查问题时一眼就能定位,而不是在十几个服务里翻消息的来龙去脉。

## 五、本地消息表:最容易落地的最终一致

回到开头那次对账事故,根子在于**"扣款"和"改余额"这两个动作不在一个事务里**,中间又隔了消息或 RPC。本地消息表的解法是:**把"要通知下游"这件事,也变成本地事务的一部分**。

```sql
-- 同一个本地事务里,业务数据 + 消息一起落库
INSERT INTO orders(order_id, amount, status) VALUES (?, ?, 'PAID');
INSERT INTO msg_outbox(msg_id, payload, status) VALUES (?, ?, 'PENDING');
-- 事务提交,两者要么都成功,要么都失败
```

核心就一句话:**本地事务提交后,再由一个定时任务(或 MQ)扫 `msg_outbox` 里 `PENDING` 的消息,投递给下游;下游消费成功,把消息置为 `SENT`**。

伪代码长这样:

```java
// 1. 业务方:本地事务里写业务 + 写消息
@Transactional
public void pay(Long orderId) {
    orderDao.markPaid(orderId);                 // 改订单状态
    outboxDao.insert(orderId, "OrderPaid");     // 写本地消息表
}

// 2. 投递方:定时扫未投递的消息
public void deliver() {
    for (Message m : outboxDao.findPending()) {
        mq.send(m);                              // 投递
        outboxDao.markSent(m.getId());           // 标记已发送
    }
}

// 3. 下游:消费方保证幂等
public void onOrderPaid(Long orderId) {
    if (accountDao.alreadyProcessed(orderId)) return;  // 幂等去重
    accountDao.deduct(orderId);
}
```

这套方案之所以被叫"首推",是因为它**实现简单、没有协调者、天然最终一致**。代价是必须啃下两块硬骨头:

- **重复投递**:投递成功但没来得及标 `SENT` 就重启,消息会重发 → 下游要幂等
- **消息可能乱序/延迟**:消费方要能容忍中间态的短暂不一致

> 幂等是本地消息表的生命线。宁可让下游多查一次"这事处理过没",也别假设消息只会来一次——见过的重复消费,十有八九都是栽在这。

## 六、一次说清:到底怎么选

把几种方案摆在一起看:

| 方案 | 一致性 | 锁/阻塞 | 业务侵入 | 适用场景 |
|------|--------|---------|----------|----------|
| 2PC/XA | 强 | 高,同步阻塞 | 低 | 高一致性、低并发(核心账务) |
| TCC | 强(业务保证) | 低 | 高 | 资金/库存,预留语义清晰 |
| Saga | 最终 | 无 | 中 | 跨服务长流程 |
| 本地消息表 | 最终 | 无 | 低 | 大多数通用场景的首选 |

选型有一条简单的判断路径:**先问能不能接受最终一致**——大多数业务能,那就优先本地消息表;确实要强一致,再问语义适不适合"预留-确认",适合才上 TCC;只有那种一致性要求苛刻、并发又不高的封闭系统,才轮到 2PC/XA。

提到 Seata,它本质上是把上面几种模式做成了开箱即用的中间件(AT 模式近似 2PC、TCC 模式对应 TCC、Saga 模式对应 Saga)。但理解了原理再看它,会发现它不过是把"协调者、全局锁、补偿"这些脏活替你包了——**选型判断并不会因为用了哪个中间件而改变,变的只是实现成本**。

## 写在最后

分布式事务没有银弹,只有取舍。回头看,真正值得记住的还是那几句:

1. **能用最终一致,就别硬上强一致**——强一致的成本(锁、阻塞、单点)是实打实的
2. **能用本地消息表,就别急着上 TCC**——除非"预留-确认"语义天然存在
3. **无论哪套方案,幂等和补偿都是绕不过去的**——把这两件事想清楚,方案才对了一半

选型之前,先回到业务本身问一句:"这里到底需要多强的一致,又愿意为它付多少代价?"答案往往比套哪个框架更重要。
