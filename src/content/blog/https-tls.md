前阵子凌晨收到一堆告警:一个对外的网关服务,所有 https 请求全部握手失败,客户端报 `certificate verify failed`。查了半天,原因简单得让人有点无语——**服务器证书过期了**,而且过期了整整三天。更糟的是,备用机房的证书是另一套,早一个月就过期了,所以切换过去也没用,等于全网跪了一次。

这件事之后,把 HTTPS 和 TLS 从头到尾又捋了一遍。这篇文章就把搞懂的原理、踩过的坑,一次讲清楚。

## 一、为什么需要 HTTPS

明文 HTTP 有三类风险,分别对应 HTTPS 的三件武器:

| 风险 | 含义 | HTTPS 怎么解决 |
|------|------|----------------|
| 窃听 | 传输途中被人截获内容 | 对称加密 |
| 篡改 | 数据被中间人改动 | 消息认证码(MAC) |
| 冒充 | 无法确认对方是不是真服务器 | 证书 + 非对称加密 |

一句话:**加密解决窃听,签名解决篡改,证书解决冒充**。三件事缺一不可,很多人只盯着"加密",忽略了另外两个。

## 二、对称加密与非对称加密,为什么不能只用一种

先看两种加密的本质区别:

- **对称加密**:加解密用同一把钥匙,速度快,但"钥匙怎么安全地交给对方"这个问题它自己解决不了
- **非对称加密**:公钥加密、私钥解密,能安全地协商密钥,但算法慢,扛不住大流量

直觉上,要么全对称、要么全非对称,但两边都有死穴:

> 只用对称加密,钥匙在网络上裸奔,等于没加密;只用非对称加密,性能差到不可接受。

所以 HTTPS 用的是**混合加密**——这也几乎是所有安全协议的标准套路:

1. 先用非对称加密(慢,但只用一两次)协商出一把"会话密钥"
2. 之后的数据传输,全部改用这把对称密钥(快)来加密

既安全,又扛得住性能。

## 三、证书链:信任是怎么层层传递的

对称/非对称解决了"怎么加密",但还有个更根本的问题没解决:**第一次通信时,你怎么知道对方出示的公钥真的属于它?**

答案是一张证书。证书里装着一堆字段,核心是这几样:

- **Subject**:证书属于谁(域名/组织)
- **公钥**:非对称加密要用的那把
- **签发者**:这张证书是谁签的
- **有效期**:`notBefore` / `notAfter`,过期的证就是那次事故的元凶
- **签名**:用签发者私钥对上面所有内容算出来的值

浏览器拿到证书后,做的事其实很朴素:**用签发者的公钥去验签**。验签通过,说明证书内容没被改过,而且确实由这个签发者背书。可"签发者的公钥"又凭什么可信?

这就引出了**证书链**。信任不是凭空来的,而是从"系统里预置的根证书"一路锚定下来的:

```
根证书(Root CA,预置在系统/浏览器)
   └── 中间证书(Intermediate CA,由根签发)
          └── 站点证书(Leaf,由中间签发,就是你的域名证书)
```

- 根证书是信任的**起点**,出厂就埋在操作系统和浏览器里,数量少、被严密保护
- 站点证书是信任的**终点**,就是平时花几千块/一年去 CA 那里买的那个
- 中间证书是桥梁,负责隔离:根证书的私钥几乎永远离线,出事也不至于全盘作废

> 一个基本原则:浏览器只信它内置的根证书。你的站点证书本身再漂亮,只要链上断了——比如中间证书没配全——浏览器照样报"不受信任"。

这一点踩过坑:**只配了站点证书、漏了中间证书**,Chrome 在有的机器上正常、有的机器报错,排查起来特别抓狂。原因是部分客户端缓存过中间证书,掩盖了问题。

## 四、TLS 握手:一次连接的完整流程

TLS 1.2 的经典握手(以 ECDHE + RSA 为例)大致四步:

```
客户端                                        服务器
   │── 1. ClientHello(随机数、支持的算法套件) ──▶│
   │◀── 2. ServerHello(随机数、选定套件) + 证书 ─│
   │◀──── 3. 服务端用私钥对密钥交换参数签名 ────│
   │── 4. 双方各自算出会话密钥,开始加密通信 ────▶│
```

关键点拆开看:

1. **ClientHello**:客户端把随机数、支持的密码套件(如 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`)发给服务端
2. **ServerHello + 证书**:服务端选定套件、返回自己的随机数和证书
3. **密钥交换**:双方通过 ECDHE 各自算出一份相同的**预主密钥**,再结合前面两个随机数,推导出会话密钥
4. **完成**:发一个 `Finished` 消息互相确认,之后进入对称加密传输

第 3 步是整套机制的精髓:**真正的会话密钥从来不在网络上明文传输**,双方是"各自在本地算出来的",中间人截不到。

TLS 1.3 更激进,把握手压缩到了 **1-RTT**,密钥交换固定用 ECDHE,还把 RSA 密钥交换彻底干掉了(只留 RSA 做签名)。所以现在新项目,能上 1.3 就上 1.3。

## 五、中间人攻击,到底怎么防

所谓中间人攻击(MITM),就是攻击者站在客户端和服务器之间,两边骗。经典剧本:

```
客户端  ──▶  中间人  ──▶  服务器
         ◀──  伪造证书/截获密钥  ◀──
```

如果只是"窃听"还好防——数据加密了,他只能看到密文。真正危险的是**主动攻击**:

1. 攻击者截下服务器发给客户端的证书,换成自己的伪造证书
2. 客户端如果用攻击者的公钥加密会话密钥,攻击者就能解密,再转发给真服务器
3. 于是攻击者拿到了完整的会话密钥,后面全裸奔

**防线只有一条,就是证书校验**。伪造的证书拿不到根 CA 的签名,浏览器验签立刻失败,弹出"您的连接不是私密连接"。

这也解释了为什么自签名证书会被告警:它不是"不安全",而是**浏览器无法通过内置根证书验证它是谁**,信任链断了。公司内网里自建 CA、再把自建根证书下发到每台机器,就能让自签证书"合法化"——这是内网常见做法。

## 六、证书配置:openssl 命令 + nginx 配置

原理讲完了,下面是能直接抄的部分。

### 6.1 生成自签名证书(内网/测试用)

```bash
# 一键生成私钥 + 自签名证书,有效期 365 天
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout server.key \
  -out server.crt \
  -days 365 \
  -subj "/CN=example.com"
```

### 6.2 从 CA 申请证书的标准流程

```bash
# 1. 生成私钥
openssl genrsa -out server.key 2048

# 2. 生成证书签名请求(CSR),把 CSR 交给 CA 签发
openssl req -new -key server.key -out server.csr

# 3. 拿到 CA 签发的证书后,本地验一下链是否完整
openssl verify -CAfile ca-bundle.crt server.crt
```

第 3 步强烈建议加到发布流程里,`verify` 通过,才能上。

### 6.3 检查线上证书,几行命令

```bash
# 看证书有效期、签发者、域名
openssl s_client -connect example.com:443 -servername example.com \
  | openssl x509 -noout -dates -subject -issuer

# 快速验一下证书链是否配全(重点看中间证书在不在)
openssl s_client -connect example.com:443 -showcerts
```

### 6.4 nginx 侧的标准配置

```nginx
server {
    listen 443 ssl http2;
    server_name example.com;

    # 站点证书 + 私钥(私钥权限必须 400,root 持有)
    # 更推荐:用 fullchain.crt(站点+中间证书合成一个文件),链才完整
    ssl_certificate     /etc/nginx/certs/fullchain.crt;
    ssl_certificate_key /etc/nginx/certs/server.key;

    # 只开 TLS 1.2 / 1.3,关掉老旧的 1.0 / 1.1
    ssl_protocols TLSv1.2 TLSv1.3;

    # 指定密码套件,优先 AES-GCM / ChaCha20
    ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-CHACHA20-POLY1305';
    ssl_prefer_server_ciphers on;

    # 复用会话,减少后续握手开销
    ssl_session_cache    shared:SSL:10m;
    ssl_session_timeout  10m;
}
```

三个特别容易漏的点:

1. **私钥和证书要成对**,配错了服务直接起不来,还报一堆看不懂的错误
2. **中间证书必须配**,用 `fullchain.crt` 最省心,这是前面提到的"漏配中间证书"事故的正解
3. **关掉 TLS 1.0 / 1.1**,它们早已被各浏览器标记不安全,留着反而过不了安全审计

## 七、线上还有哪些坑要盯

除了证书过期,还有几个高频问题:

- **证书链不完整**:漏中间证书,部分客户端报错,诡异且难查
- **私钥泄露**:私钥一旦出去,证书立刻作废重签,等不了一天
- **混合内容**:页面走 HTTPS,但里面引了 `http://` 的图片/脚本,浏览器直接屏蔽或降级

一个更推荐的做法,是把**证书的申请、续期、下发做成自动化的**,现在有 Let's Encrypt + ACME 协议,配合 certbot 就能自动续期,彻底告别"忘了续证"这种低级事故。

## 写在最后

回头总结,HTTPS 要记住的核心其实就三句话:

1. **对称加密传输数据、非对称加密协商密钥**,混合着用,性能和安全性都要
2. **信任靠证书链层层锚定**,断在中间证书这种小地方,一样全线告警
3. **证书是资产,不是一次性配置**,过期、泄露、链不完整,每个都得盯住

原理讲得再透,都不如一句落地:**把证书当成有生命周期的资产去管理**,而不是配完就忘在 nginx 里。
