有次一个团队上线,代码 push 完、构建通过、部署完成,页面一打开直接白屏。追了半天,是本地 `node_modules` 里有、但 `package-lock.json` 没锁住的一个依赖,在 CI 环境里版本对不上。这种"本地能跑、线上崩"的事,见过太多次了,根子都指向同一件事:**没有一条可靠、可重复的流水线**。

CI/CD 听起来高大上,核心就一句话——**代码提交后,自动完成构建、测试、部署,把人从重复又容易出错的体力活里解放出来**。这篇把一条流水线从头到尾拆开讲。

## 一、先分清 CI 和 CD

这两个词经常连在一起说,但它们解决的是两个不同的问题:

| 概念 | 全称 | 干什么 | 核心价值 |
|------|------|--------|---------|
| CI | Continuous Integration | 每次提交自动构建 + 测试 | 尽早发现问题 |
| CD | Continuous Delivery/Deployment | 通过测试的代码自动部署 | 缩短交付周期 |

一句话:**CI 负责"证明这代码是好的",CD 负责"把这好代码送上线"**。别一上来就想着全自动化部署,先跑通 CI,再逐步加 CD,这是更稳妥的路径。

## 二、一条能直接抄的流水线

以 GitHub Actions 为例,`.github/workflows/ci.yml`。这个配置已经踩过不少坑,该加的门禁都加上了:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '17'

      # 关键:用 mvnw 而不是 mvn,锁定 Maven 版本,避免环境差异
      - name: 构建
        run: ./mvnw -B clean package -DskipTests

      - name: 单元测试
        run: ./mvnw -B test

      # 质量门禁:代码覆盖率不达标直接失败
      - name: 覆盖率门禁
        run: ./mvnw -B jacoco:check

      - name: 构建镜像
        run: docker build -t my-app:${{ github.sha }} .

      - name: 推送镜像
        run: docker push my-app:${{ github.sha }}
```

几个容易忽略的点:

- **用 `./mvnw`(wrapper)而不是全局 `mvn`**。见过 CI 里装的是 Maven 3.8,本地是 3.9,某些插件行为不一致,构建结果对不上。wrapper 把版本锁死,从根上消除差异。
- **镜像 tag 用 `github.sha`(commit 哈希)而不是 `latest`**。`latest` 看起来方便,但出了问题你根本不知道线上跑的是哪个 commit,回滚都无从谈起。
- **敏感信息一律走 `secrets`**。密码、token、私钥如果硬编码进仓库,一旦仓库权限失控就是裸奔。GitHub Actions 里用 `${{ secrets.XXX }}` 注入,仓库里只留引用不留明文。

## 三、Git Flow:分支该怎么玩

流水线是"怎么跑",分支策略是"代码怎么组织"。一个常见做法是简化版的 Git Flow:

- `main`:永远可发布,只能通过 PR 合入,禁止直接 push
- `develop`(或 `feature/*`):日常开发
- `hotfix/*`:线上紧急修复

对应到流水线上,分支策略和触发时机是绑定的:

| 分支 | 触发动作 | 结果 |
|------|---------|------|
| `feature/*` | push | 只跑构建 + 测试 |
| `main` 的 PR | pull_request | 跑完整门禁,作为合并前提 |
| `main` | push | 通过后自动部署 |

一个基本原则是:**`main` 分支加保护,合并前必须通过 CI**,任何人(包括管理员)都不能绕过。

## 四、质量门禁:别让流水线只"能跑"

流水线最大的误区,是**只关注"能不能构建成功",忽略了"这代码质量够不够"**。真正的门禁,是把质量标准写成机器可判定的规则,卡在合并之前:

```bash
# 以 Java 项目为例,jacoco 覆盖率检查
# pom.xml 里配好 rule:行覆盖率 < 80% 就 build fail
mvn clean test jacoco:check
```

门禁一般分几层:

1. **编译 + 单测**:最低要求,失败就阻断
2. **静态扫描**:如 SonarQube,查 bug、坏味道、安全漏洞
3. **覆盖率**:定一个团队认可的阈值,守住基线
4. **依赖审计**:检查有没有已知漏洞的依赖(如 `npm audit`、`dependency-check`)

> 门禁的意义不在于"卡人",而在于把"代码写得烂"这件事,从"事后被人骂"变成"提交时被机器拦住",成本最低。

## 五、回滚:出事了怎么办

流水线跑得再顺,部署上去也总有翻车的时候。真正拉开团队差距的,是**出事之后多久能恢复**。见过最狼狈的场景,是线上挂了,一群人围着讨论"上一个版本到底是啥、怎么退回去",讨论半小时。

更推荐的做法,是把回滚做成**一条和部署对等的自动化动作**:

```bash
# 部署到 K8s 的简化回滚思路:记录上一个版本,一键回退
# 部署前先存下当前版本的 deployment yaml
kubectl get deployment my-app -o yaml > backup/prev.yaml

# 新版本出问题,直接回滚到上一个版本
kubectl rollout undo deployment/my-app
```

几个关键点:

- **版本必须可标识**:前面说镜像 tag 用 commit 哈希,就是为这一刻准备的。知道线上是哪个 commit,才知道该退回哪个。
- **部署策略选好**:蓝绿、金丝雀(灰度),比"一把梭全量发布"安全得多,出问题影响面小。
- **回滚要演练**:回滚脚本平时不练,真出事一定手忙脚乱。定期做一次故障演练,比写十篇文档都管用。

## 六、落地顺序:别一上来就追求完美

见过不少团队,CI/CD 立项时雄心勃勃,要一步到位做全套自动化部署 + 灰度 + 可观测,结果半年没落地。更务实的推进方式是分步走:

1. **先 CI**:push 后自动构建 + 单测,先把"能不能编译"这个问题自动化
2. **再门禁**:加覆盖率、静态扫描,让质量卡在提交阶段
3. **后 CD**:从"自动部署到测试环境"开始,再逐步到生产
4. **最后补回滚和监控**:流水线稳定后,把应急能力补上

每一步都能独立看到价值,团队才愿意继续往下走。

## 写在最后

回头看,一条好的 CI/CD 流水线,价值不在"自动化"这三个字本身,而在它逼着团队回答了几个绕不开的问题:代码质量的标准是什么、发布流程是怎样的、出事了怎么恢复。

真正值得记住的,就三句话:

1. **用 `./mvnw`(或等价 wrapper)锁版本、用 commit 哈希锁镜像**,别让"本地能跑"变成线上事故
2. **门禁卡在合并之前**,质量问题越早发现成本越低
3. **回滚要和部署一样自动化**,出事了能几分钟内恢复,才算真的配得上"持续交付"

流水线不是一次性搭好就完事的,它是跟着团队一起长出来的。先跑通 CI,再谈 CD,剩下的交给时间。
