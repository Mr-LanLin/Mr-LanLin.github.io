> 从一次多维筛选说起，看读模型分离、最终一致、延迟规避如何各司其职

## 引子

招标大厅是招采系统里最「看脸」的一个入口：承运商进来要按线路、车型、吨位、报价截止时间、资源类型、状态……十几个维度自由组合地筛、排、翻页。这种查询有个典型的矛盾——**维度越多，越灵活，就越不适合关系型数据库**。十几个 `OR`/`LIKE`/范围条件的组合，索引要么建不过来，要么命中率极低，大厅列表一慢，整个系统的体感就垮了。

但大厅要「快」，不代表数据可以「不准」。列表上的价格、状态、报名人数，任何一个数字错了，都可能引导承运商做出错误的投标决策。

于是存储层必须回答两个看似冲突的问题：**怎么查得快，又怎么保证准。** 本文拆解这套「快准分离」的读架构——它没有发明什么新东西，而是把「读模型与写模型分离」这个老思想，用到招标大厅这个具体场景里，落地成一套可自愈、可灰度的存储设计。

---

## 一、读模型与写模型分离：最根本的一招

一切性能优化的底层，都是「读写分离」。但这里说的不是「主从读写分离」，而是更深一层的**模型分离**：

- **写模型追求「准」**：数据要权威、要能约束、要支持事务。这条路径用关系型数据库，数据是规范化的，改动最小、最不易错。
- **读模型追求「快」**：数据要贴合查询的形态，字段要冗余、要预计算、要贴近过滤条件。这条路径用搜索引擎，数据是「为查询而生」的宽表。

两个模型是同一个事实的两种投影，中间靠一条「事实流」对齐。这个思想有两个别名，一个叫 CQRS（命令与查询职责分离），一个叫「读写模型的最终一致」。

落到招标大厅：

```text
写路径：  报价/报名/改状态  →  MySQL（权威、事务、规范化）
读路径：  大厅多维筛选      →  ES（宽表、倒排、多维过滤）
对齐：    MySQL 的变更     →  binlog 事实流  →  异步同步到 ES
```

为什么要分成两个模型，而不是让 ES 直接当主库、或者让 MySQL 硬扛查询？因为两者谁都替代不了谁：MySQL 扛不住十几个维度的自由组合查询，ES 也扛不住强事务和强约束。**让每个存储干它最擅长的事，代价是把「强一致」降级成「最终一致」——这个代价，用一条可靠的同步链路去兜住。**

## 二、快准分工：ES 管过滤，MySQL 管取值

「快」和「准」的分工，不只是「列表走 ES、详情走 MySQL」这么简单，而是精确到「一次查询内部」：

**第一步，ES 负责「筛」。** 大厅的多维过滤、排序、分页，全部压给 ES。为了这一步够快，ES 里的文档是张「宽表」——把列表页要展示的字段（线路、车型、吨位、截止时间、状态、报名数……）都冗余进去，查询时零 join、纯倒排。十几维度的组合条件，在倒排索引上就是一次多条件布尔检索，毫秒级返回。

**第二步，MySQL 负责「准」。** ES 拿到的是「哪些标的中了」，但列表上真正要展示的权威数据（尤其价格这种敏感字段、实时状态这种易变字段），不能信 ES 那份可能滞后的副本，而是**用 ES 筛出来的 id 集合，回 MySQL 批量取一次权威值**，再组装返回。

```text
用户发起大厅查询
  → ES 多维过滤 + 排序 + 分页  →  命中 id 集合
  → 用 id 集合回 MySQL 批量取权威字段
  → 组装返回
```

这一步的关键认知：**ES 在这里不是 MySQL 的「替代品」，而是 MySQL 的「索引投影」。** 它把「海量候选里快速定位到一小撮目标」这个最贵的活接走，把「这一小撮目标的准确值」交还给 MySQL。两者各干一半，快与准就都有了。

这也意味着：ES 里可以大胆冗余、大胆按查询形态塑形，因为它不承担「权威」的职责，错了有 MySQL 兜底；MySQL 保持规范化和权威性，因为它只在「筛完之后」被精确点查，量小、命中主键，慢不了。

## 三、binlog 最终一致：事实流、幂等、批量、兜底

「分」容易，「对齐」难。写进 MySQL 的变更，怎么可靠地、尽量快地反映到 ES？答案是**把 binlog 当事实流来订阅**。

binlog 是数据库层面天然的顺序变更日志，它有两个价值：一是**完整**（每笔写都有记录），二是**有序**（按提交顺序）。订阅它，就拿到了「数据到底变成了什么样」的权威事实流。

但要让它可靠地驱动 ES 同步，有四个必须做对的点：

**其一，幂等。** 同步过程会重试、会重复消费，同一笔变更可能被处理多次。ES 的写入天然是「按文档 id 覆盖」，同一 id 写两次结果一致，所以幂等在这里是「顺带」满足的——只要文档 id 用的是业务主键，而不是自增的插入序号。

**其二，批量合并。** 最后时刻的洪峰里，同一批标的的 binlog 会密集到达。一条一条处理，同步开销大、回源查询多。正确的做法是**先聚合再回源**：把一批 binlog 里涉及的标的 id 去重、合并，一次性从 MySQL 批量取回最新的权威数据，再批量写 ES。一条 binlog 是「通知」，真正的数据从 MySQL 批量重取，而不是逐条搬运 binlog 里的旧值。

```text
binlog 批量到达
  → 过滤掉无关变更，聚合出「受影响的主键集合」
  → 用主键集合回 MySQL 批量取最新权威数据
  → 批量写 ES（按文档 id 覆盖，天然幂等）
```

**其三，串行防抖。** 同一标的的 binlog 若并发触发同步，可能「先处理的旧值覆盖后处理的新值」。给同一主键的同步加一把「排队合并」的锁——同一时刻只同步一次，期间到达的变更合并到下一次。这既防了并发覆盖，又省了重复回源。

**其四，全量对账兜底。** 无论同步链路多可靠，总有极端情况：binlog 消费中断、程序重启丢消息、历史数据没有 binlog。所以必须有一条**离线的全量对账**通道——按主键游标扫 MySQL，和 ES 里的文档逐条比对、补偿缺失或过期的记录。它是最终一致的「最后一道保险」，让「最终」二字真的能兑现，而不是「可能迟到、可能缺席」。

最终一致的本质，不是「接受不一致」，而是**用一条「增量同步 + 全量兜底」的双轨链路，把不一致的概率压到可忽略、把不一致的时间压到足够短。**

## 四、强一致场景绕开 ES：详情页直走 MySQL

最终一致有一个永远绕不开的短板：**同步有延迟**。ES 里的数据，永远比 MySQL 晚那么一拍——几毫秒到几百毫秒不等。

这个延迟，对「大厅列表」是可以容忍的：列表是「浏览」，用户扫一眼筛出候选，晚几百毫秒刷新出来没关系，而且列表本来就高频刷新。

但对「详情页」是致命的：详情页上的**报价金额、投标状态、剩余次数**，是用户下一秒就要据此做决策的关键数据。如果用户刚报完价，回到详情页看到的还是旧价格、旧状态，轻则困惑，重则重复报价、误判排名。

所以详情页的读，**直接走 MySQL，不走 ES**：

```text
大厅列表  →  ES 筛 id  →  回 MySQL 取列表字段   （能容忍最终一致）
标的详情  →  直接 MySQL 主键点查               （必须读到即正确）
```

这条「绕过」不是技术洁癖，而是对「最终一致边界」的清醒认知：**最终一致适用于「读多、容忍短暂滞后」的场景，凡是「读了就要立即做正确决策」的读，一律回权威源。** 划清这条边界，才能放心地把大厅这种重查询交给 ES，而不担心一致性「漏」到不该漏的地方。

顺带一提，写路径天然是强一致的——报价、报名、改状态都落在 MySQL 的事务里，MySQL 是唯一的权威源。所以「详情页直走 MySQL」其实是零额外成本的：它读的就是刚写进去的那份权威数据，不存在「该走哪」的选择题。

## 五、列表查询的异步编排：把串行等待变成并发聚合

前面说的「ES 筛 id → 回 MySQL 取数」，是一个理想的两步。但真实的大厅列表往往不止两个数据源：ES 筛出候选、MySQL 取权威字段、还要拼上「每个标的的报名人数」（可能来自另一张统计表）、「当前用户的报名状态」（可能来自缓存）……如果把这些依赖**串行**地一个一个查，每个的延迟叠加起来，列表就慢了。

更进一步的优化，是把这些**相互之间没有依赖**的数据源，改成**并发聚合**：

```text
串行（慢）：
  id集合 = ES 查询          —— 200ms
  权威字段 = MySQL 查询     —— 100ms
  报名数   = 统计查询       —— 80ms
  我的状态 = 缓存查询       —— 5ms
  总耗时 ≈ 385ms（逐项累加）

并发编排（快）：
  esFuture   = 异步执行 ES 查询
  但 MySQL 取数依赖 esFuture 的 id 集合，这是唯一的前置依赖
  其余两个查询（报名数、我的状态）与 MySQL 取数无依赖，可并行
  → 先并发发起「报名数」「我的状态」，等 esFuture 完成后再回 MySQL
  → 总耗时 ≈ max(并行支路) + 必然的串行链
```

关键在于**识别依赖关系**：哪一步必须在哪一步之后（回 MySQL 必须等 ES 的 id），哪些步骤彼此无关可以并发（统计查询、缓存查询与回源无关）。把「无依赖的支路」并发化、把「有依赖的主链」留作必然的串行，就能把「所有延迟相加」优化成「各支路延迟取最大」。

这个「异步编排」目前是规划方向，但它体现的是一个通用的性能思想：**延迟的敌人不是单个查询慢，而是把本可并发的查询排成了串行。** 识别依赖、并发聚合，是列表类接口提速最直接、也最容易被忽视的一招。

## 六、让最终一致可自愈、可灰度

最后补两个让这套架构「长期可维护」的细节，它们不显眼，但决定了系统能不能放心地演进。

**索引别名与无缝切换。** ES 索引会重构：字段变了、分词器调了、mapping 要改。硬切索引会造成空窗或数据丢失。正确做法是给索引挂「别名」，查询永远指向别名，而不是物理索引名。重构时新建索引、灌数据、对账通过后，把别名一次性切过去——新旧索引并存，切换零停机，出问题还能秒回滚。这套机制，也是「双版本 ES 灰度」的基础：新旧两个索引并存，用开关控制流量逐步切，出问题关开关即可。

**全量对账的周期化。** 增量同步负责「快」，全量对账负责「兜底」，但兜底不能只在出事时才想起。把它做成周期任务，闲时静默跑、忙时降频，让 ES 和 MySQL 的「账」始终对得上。对账发现的不一致，既是补偿的依据，也是同步链路健康度的度量——差异率长期为零，说明增量链路稳；差异率突然抬头，就是告警信号。

## 收尾

回看这套读架构，它没有用什么高深的技术，全靠几个朴素的取舍：

- **分**：读模型和写模型分开，让 ES 管快、MySQL 管准，各干各最擅长的事。
- **合**：用 binlog 事实流把两者对齐，靠幂等、批量、串行、全量对账四条，把「最终一致」从口号变成可兑现的承诺。
- **避**：划清最终一致的边界，强一致场景（详情页）绕开 ES 直走权威源。
- **并**：列表查询识别依赖、并发聚合，把串行等待压成并行聚合。
- **稳**：索引别名、全量对账，让这套架构可以安全地演进、自愈、灰度。

存储架构的精髓，从来不是「选了哪个存储」，而是**想清楚每类数据要「快」还是要「准」，然后为它匹配最合适的存储，再用一条可靠的对齐链路把分歧缝合。** 快与准的矛盾，最终不是被某一款数据库解决，而是被一套「分工 + 对齐 + 规避」的读架构消化掉的。
